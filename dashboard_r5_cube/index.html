10. Optimizer Summary

  
Top-line output from scripts/optimize_strategies_from_cube.py (Batch 388 + Batch 391). The KPIs below + the markdown report come from this script.


  
  

    What do these KPIs and L1 / L2 / L3 mean? (click to collapse)
    

      
Source dir. Which cube directory the optimizer read. output_r5_merged_<range>/ = the merged Phase 1A-beta cube run. output_optimization_candidates_2026_05_28/ is where the per-strategy JSONs + this summary were written.


      
Bucket counts. The optimizer classifies every strategy that fired in the cube into one of three Lens-B verdicts based on the DEC-426 5-Gate (n >= 30, p < 0.05 Bonferroni, PSR >= 0.95, t >= 3.4, R:R >= 2.0). Buckets:

      
    
        
  • PASS-strict - clears all 5 gates including PSR. Eligible for the 1A-alpha gate.
    • 
        
  • PASS-relaxed - clears 4 of 5 (PSR < 0.95). Common bucket; statistically promising but not strict.
    • 
        
  • FAIL - clears fewer than 4 gates. Strategy is unlikely to survive walk-forward.
    • 
      


      
L1 / L2 / L3 - three layers of cube analysis. The same trade data is sliced three different ways:

      
    
        
  • L1 - Per-exit-method aggregate. For each of the 26 exit methods, pool ALL strategies that used it and compute aggregate Sharpe / PF / WR. Answers: "which exit method is best on average?" Useful as the default exit when a specific strategy doesn't have a clear cell winner.
    • 
        
  • L2 - Per-(strategy x exit_method) cell. The headline lens. For every (strategy, exit_method) cell with n >= 5 trades, compute the 5-Gate verdict. Tab 13 (Cell Cube) is the sortable view; this is where STRATEGY_EXIT_OVERRIDE candidates come from.
    • 
        
  • L3 - Parameter-variant winner within a family. When a strategy has cells in multiple variants of the same exit family - e.g., time_stop_10d vs time_stop_20d, or r_multiple_2r vs r_multiple_3r, or trailing_5pct vs trailing_10pct vs trailing_15pct - L3 picks the winning variant per strategy. Answers: "given this strategy uses some-kind-of-time-stop, which exact day count works?"
    • 
      


      
1A-alpha gate. Owner-set gate: at least one strategy must show rules-only OOS Sharpe >= 0.7 in at least one regime under 4-fold walk-forward. The R5 OOS gate verdict is computed on the final merged 614-ticker cube and surfaced in Tab 5 / Tab 13; do not read a hardcoded number here. If a cell clears >= 0.7 OOS in >= 1 regime the gate opens and Phase 1B-alpha ($300 Haiku agent overlay budget) becomes eligible. If not, loop back to entry-side optimization (Dim A thresholds, Dim B compound logic) and re-cube.


      
Quick read order: KPIs (overall bucket counts) -> Tab 13 Cell Cube (sort by Sharpe DESC; look for 5-Gate strict passes in the top rows) -> Tab 11 Candidates (drill into a specific strategy to see its 9-dim findings) -> come back here to see the markdown report's recommendations.

12. Quiet Strategies (producer-zero audit)

  
Strategies with 0 fires in cube. Per producer_zero_post_cube_audit.json: 3-bucket classification by gate-key empirical emission.


  
  

    What do these buckets mean? (click to collapse)
    

      
The setup. A strategy is a list of entry conditions joined by AND (e.g. near_52w_high AND price_above_ema_200 AND resistance_break_retest). Each condition has a "producer" - the function that computes whether the condition is true today on this ticker. If a strategy fires zero trades in a backtest, it's "quiet". The optimizer (producer_zero_post_cube_audit.json) classifies the reason into one of three buckets so you know whether to fix the producer, restructure the rules, or loosen a downstream gate.


      
1. PRODUCER_LAYER_ZERO_LIKELY (broken signal feed).

      
At least one of the strategy's clauses NEVER returns truthy on any day or ticker in the backtest window. The producer is silently broken: bad data path, schema drift, exception caught and discarded. The strategy can't fire because its required ingredient is missing.

      
Example. SMC clauses depend on compute_smc_signals in backtest/signals/smc_ict.py. If the vendored library fails to import in the AWS environment, every SMC clause returns false silently. Batch 416 wired diagnostic logging so the actual failure mode shows up in backtest.signals.screener logs at the next cube re-run.

      
Fix: repair the producer (data path, schema, import) - not the strategy rules.


      
2. COMPOUND_RESTRICTIVE (clauses fire alone but AND never satisfies).

      
Each individual clause emits truthy on a reasonable share of days/tickers, but when you AND them all together the joint condition almost never happens. Everyday analogy. "I want to go for a run if it's sunny AND between 60-70F AND weekend AND my running partner is free AND I had at least 7 hours sleep." Each individual condition is common; the AND of all 5 might happen twice a year.

      
Trading example. A strategy with clauses near_52w_high (fires 8% of ticker-days), price_above_ema_200 (60%), resistance_break_retest (5%). Each clause is fine on its own. But the AND - multiplied with correlation discount - lands around 0.1% of ticker-days, then liquidity/sector/regime gates trim further until zero trades.

      
Fix: open Tab 11 -> pick the strategy -> dimension_b_compound section shows per-clause fires_at rates. The restrictive array is the AND-killer (low fire rate). The always_on array fires ~100% of the time - those don't add any restriction, drop them. The proposals array is the optimizer's suggestion.


      
3. SKIPPED_AT_ENGINE (downstream gate kicks the trade).

      
The strategy DOES generate candidate trades that pass the screener, but a downstream engine gate rejects them: liquidity floor (ADV too low), position-size cap full, daily-cash limit, ticker-uniqueness (already in a position on this ticker), confidence tier too low.

      
Example. A small-cap momentum strategy generates 30 candidates a day on illiquid tickers. ADV floor rejects all 30. Strategy looks quiet from the outside.

      
Fix: Tab 8 (Skipped) shows reason codes per skipped trade. Either loosen the gate (e.g. tier the strategy to a smaller-cap universe with a lower ADV floor) or accept the strategy is incompatible with current rules.


      
Quick decision rule: PRODUCER fix the data; COMPOUND restructure the rules; SKIPPED loosen the downstream gate or move the strategy to a more permissive tier.

        PRODUCER_LAYER_ZERO_LIKELY

        Why are there so few rows in Tab 13 Cell Cube?
        
      
        Theoretical ceiling: 5,694 cells per regime (219 strategies x 26 exit methods). The populated cell count is read live from the merged R5 cube.
        
      
        Cube replay mechanics (corrected Batch 442). Each entry the strategy fires gets written to trade_log.csv once (closed via its primary exit). The cube replay then simulates that entry through ALL 26 exit methods - producing trade_exit_detail.csv with one row per (trade x exit_method). So if a strategy fires 100 entries, trade_exit_detail has 100 x 26 = 2,600 rows for that strategy. The L2 groupby (strategy, exit_method) produces 26 cells per strategy, each cell containing the same 100 trades - so n = 100 in every cell, NOT divided across exits. Each entry gets multiplied by 26, not divided.
        
      
        How many cells are populated? The populated cell count is read live from the merged R5 cube; a strategy has up to 26 exit cells (one per exit method) but only those reaching the n threshold appear. The cause is degenerate cells filtered out for reasons that are real bugs, not structural limits:
        
      
          
        
        • scripts/optimize_strategies_from_cube.py::analyze_exit_methods Layer 2 excludes every cell with n < 5 trades (this is the only structural filter).
          • 
        
        • Pre-Batch-415 bug: exit_earnings_blackout always returned "no_earnings_known" because signals_at_entry dict was missing ticker - so every cell using earnings_blackout had constant exit reason and got dropped as degenerate.
          • 
        
        • Pre-Batch-415 bug: exit_class_time_stop defaulted to "momentum" for every strategy because strategy_name wasn't in the signals dict either - same constant-exit -> degenerate filter.
          • 
        
        • Pre-Batch-416 silent failures: SMC-derived strategies produced empty replays where SMC keys were absent - those cells had n=0 and got filtered.
          • 
        
        • Some exits genuinely don't apply (e.g., earnings_blackout on a strategy that never trades near earnings -> 0 trades hit the blackout window -> n=0).
          •
