# Strategy Optimisation Runbook — class level, for every strategy

This runbook is the procedure for optimising ANY strategy in the registry. **It names no strategy,
family, config or campaign.** A rule written around one campaign gets copied as that campaign's
values: the owner ruled a family-specific Step-2 procedure a serious error on 2026-09-23 and
directed this class-level form on 2026-09-24. Everything strategy-specific lives elsewhere:

| record | where |
|---|---|
| measured instances, dated slates, per-family decisions and results | `STRATEGY_CAMPAIGN_LOG.md` |
| each strategy's Table A (depth + breadth bands, generated) | `strategy_optimisation/` (its README is the band charter) |
| which strategies are optimised, and which lane each is in | `STRATEGY_OPTIMISATION_STATUS.md` (generated by `scripts/build_strategy_status.py`) |
| admitted lines | `PHASE_1B_ROSTER.md` + `output_audit/phase_1b_step2_admissions.json` |
| the pre-restructure runbook, verbatim | `archive/2026-09-24-strategy-optimisation-plan-pre-B3096/STRATEGY_OPTIMISATION_PLAN.md` |

Every heading carries its pre-restructure anchor as "(formerly §x)", so a citation written before
B3096 - in LEARNINGS, the queue, a generated Table A file or a script comment - still resolves by
search. **APPENDIX M** maps every old section to its new home.

**Adding a strategy-specific fact here is the defect this restructure removed.** A measured
instance, a dated slate or a family's knob values goes in `STRATEGY_CAMPAIGN_LOG.md`; this file
states the rule it instantiates. Pinned by `test_b3096_runbook_is_class_level_and_numbered_consistently`.

## 0. VOCABULARY AND NUMBERING - read this first

### 0.1 The four STEPS - the ruled numbering (owner 2026-08-29; formerly §10.1 "The four phases")

Every campaign passes through four STEPS, numbered by the ruled step table in §1.2. That table is
data, not prose: `scripts/phase_table.py` parses it and the launcher resolves each step's window
and universe from it. The steps descend from B1548's REPEATABLE WORKFLOW (formerly §10), which
superseded the original two-phase method for every strategy.

| step | name | what it does |
|---|---|---|
| **Step 0** | INVENTORY | build the SPECS entry: formula, Table A, factorial (§2) |
| **Step 1** | SEARCH | rank combinations IN-SAMPLE - a ranked list with NO gates (owner ruling B1608) |
| **Step 2** | VALIDATE | the holdout read - gate verdicts (one read offline; one per slate config under the waterfall, §1.1 item 1) |
| **Step 3** | ADMIT | a qualifier enters the Phase 1B roster on the owner's ruling (§6) |

This is the numbering the owner's rulings, the queue and the code already use: a spec's
`"step": 2` is Step 2, and `phase_table.resolve(2)` supplies its window and universe.

- **Sub-steps** are numbered inside their step: Steps 0.1-0.7 build the SPECS entry (§2.2),
  Steps 1.0-1.7 launch an engine Step 1 (§4.5), Steps 2.1-2.5 launch Step 2 (§4.9). **"§" always
  marks a section of this document and never a step** - §2.2 is a section, Step 2.2 is a sub-step
  of Step 2.
- **Workflow step ids** are lettered so they cannot collide: T0-T8 (tightening), L0-L8 (loosening),
  F1-F5 (the offline path), R1-R10 (the on-ramp), D1-D6 (the ruled waterfall decisions). The
  post-config battery's nine checks are "battery step N" (§5).
- **Two numberings existed before B3096 and are RETIRED.** The old workflow headings read STEP 0
  SPECS, STEP 1 SEARCH, STEP 2 GRADE, STEP 3 VALIDATE, STEP 4 ADMIT - one higher than the ruled
  table from grading onward - so the Step-2 launch procedure was headed STEP 3.1-3.4 and admission
  was STEP 4. Grading is now part of Step 1 (§4.6), the launch procedure is Steps 2.1-2.5, and
  admission is Step 3. APPENDIX M maps both.
- **BREADTH IS NOT A STEP.** It is the Priority-2 LEG of a campaign (§0.3): its search runs inside
  Step 1, and its cells are read inside Step 2 - in the campaign's one read when breadth runs on the
  winning line before it (§4.4 items 5-6), or in a Step-2 read of its own when the breadth leg runs
  after the depth verdict (§3.6 item 7).
- **Not the PROJECT stages.** CLAUDE.md's "Stage 2 - Strategy Validation", "Stage 3" (paper
  trading) and "Stage 4" (live) name the whole project's phases; the four steps here all sit inside
  project Stage 2 (CLAUDE.md's header: the project is at Stage 2, and Phase 1B precedes Stage 3).

### 0.2 Two workflows - TIGHTENING and LOOSENING are separate (owner 2026-09-16, B2828; restated 2026-09-24)

| workflow | what a level does | cost | section |
|---|---|---|---|
| **W-T TIGHTENING** | moves a threshold TIGHTER on a magnitude persisted in `signals_at_entry` - every level is a SUBSET of fires already recorded | zero engine hours | §3 |
| **W-L LOOSENING** | moves a threshold LOOSER, or changes a producer's own detection (FIRE-ADDING) - admits bars no cube recorded | engine resim | §4 |

Each workflow runs Steps 0-3 with its own step ids (T0-T8, L0-L8; §0.4). **Bands differ by
direction and the schema already encodes it:** tighten-side levels live in `free_band`
(subset-safe, offline), loosen-side levels in `resim_band` (engine), and `validate_spec` enforces
that the two partition the band exactly - so W-T and W-L read DIFFERENT halves of the SAME Table A
row and can never collide on a level (formerly §11.2s item 5).

A strategy's lane is the STREAM column of the status view (§0.7): `TIGHTEN` -> W-T, `LOOSEN` ->
W-L, `BOTH` -> W-T first, entering W-L only if its tighten leg (T4) graded nothing rankable (§4.1),
`NONE` -> a breadth candidate (§3.6).

### 0.3 TWO LEGS PER CAMPAIGN - DEPTH AND BREADTH (L780, owner-caught 2026-09-11; Priority 1 and Priority 2 by owner ruling B2702; formerly §11.2b2 and §11.2b2b)

Every per-strategy campaign has TWO legs, each run or explicitly waived with a recorded reason:

- **DEPTH** - the strategy's OWN knobs: its gate signals' persisted magnitudes and cutoffs (the
  `offline_level_sweep` pattern), AND every producer band in its Table A, resim included.
- **BREADTH** - companion axes from OTHER producer families, sourced from a family companion screen
  (IS-only, one BH-FDR pass, a ranked hypothesis list - never a gate, the B2657 instrument) and
  swept as tightening axes in the same Step 1 (§3.6).

**DEPTH IS PRIORITY 1, AND THE VENUE NEVER NARROWS IT (B2702, owner ruling 2026-09-12, verbatim):**
*"Step 1 / Priority 1: Test depth by analyzing all bands of existing producers - mandatory and
crucial. Priority 2 is the breadth analysis. Becomes more important if no combination from
priority 1 is likely to clear step 2 gates."* The DEPTH leg covers ALL Table A producer bands, resim
included; the original approved depth methodology is the ENGINE grid over producer bands. An
offline venue reaches only subset-safe axes and therefore CANNOT by itself complete the depth leg
of a strategy whose depth runs through producer parameters: the unreachable axes are
resim-SCHEDULED or owner-WAIVED in words at band review - and for a TIGHTEN-lane strategy the
producer-band resim legs are IN-MANDATE and run in that lane after its offline legs (owner-corrected
2026-09-16, B2843; §3.1), on the engine mechanics of §4.5 - and **no campaign closes while a
mandatory leg is unrun** - every disposition names the legs run and not run (CHECKLIST #299 /
L785). "Offline" describes a LEG'S cost, never a strategy's scope (B2843). The mechanism is the
band-coverage gate (§3.4); Step-1 discards count as testing, per the owner's words.

**Lineage.** One family got both legs only after an owner catch, and the next campaign then ran
depth-only because the rectification had been recorded family-locally (instances in the campaign
log). A campaign spec queued BEFORE a template change is re-checked against the template AT
EXECUTION. Both legs stay inside the approval flow (§0.6): bands reviewed before Step 1, one
owner-worded Step-2 read, admissions ruled.

**Three more family-born rules promoted to the template (B2672, owner class-directive 2026-09-11:
*"Class is to be rectified and not just the instance"*):**

- **CONTROL-FAMILY COMPARISON (from B2658):** a breadth axis's lift is attributed to the signal only
  after the SAME axis is swept on a control family - if the control shows the same lift, the axis
  is general structure, not the family's signal (§3.5). Run or waive-with-reason per campaign.
- **next_pivot_target BARRED as a selected exit (owner ruling 2026-09-10):** family-agnostic - use
  the best NON-npt exit that clears the gates (applied B2664 and B2668).
- **ADMISSION DE-DUP (from B2666):** every owner-ruled admission set passes the funnel's
  Jaccard-0.70 de-dup before entering the deployable count; canonical = highest holdout Sharpe,
  pruned rows keep an audit trail (§6.3).

### 0.6 APPROVAL FLOW - which word covers which step (L779, owner-mandated 2026-09-10; formerly §11.2c)

An instruction covers the steps up to the next irreversible or owner-owned gate, NEVER past it.
This is the mandatory pre-execution check for every campaign:

| stage of work | reversible? | approval that covers it |
|---|---|---|
| Family pre-gate; the Step-0.6 offline-or-engine branch | yes | campaign start ('start X', a working-order go) |
| BANDS / axis levels (Table A) | yes, but shapes everything after | the OWNER REVIEWS the bands before Step 1 (precedent: 'Table A p4 p5 p7 should have more bands') |
| Step 1 - IS-only ranked list + Table D | yes (no holdout contact) | campaign start covers it once the bands are reviewed |
| **Step 2 - the holdout read** | **NO - one-way door** | its OWN explicit word, every time ('build the reader and run step 2'; 'admit all... as long as it clears') |
| Admission to PHASE_1B_ROSTER | reversible (strike) but owner-owned | its OWN ruling per admission, or an explicit standing scope ('top 1 per strategy', 'admit all in table A') |
| NEW-GATE wiring into strategies or engine knobs | code change | per-strategy owner approval (the ask-every-time rule) |
| Engine launch | cost + hours | NEVER without the owner's launch word (standing) |

The B2660 admission doctrine (§6.2) sets the CRITERION; it does not waive the per-step APPROVALS
above. Violation lineage (L779): a campaign ran band design, the Step-2 spend and admission on
'start the queued campaign' alone; the owner caught it and ratified the admission after the fact
(2026-09-10), and this table exists so ratification is never needed again.

### 0.7 THE PER-STRATEGY STATUS VIEW - consult it before naming ANY work (B2808, owner-approved 2026-09-13; formerly §11.2b3a)

**`STRATEGY_OPTIMISATION_STATUS.md`**, regenerated by `scripts/build_strategy_status.py`, is the
single view that answers *has strategy X been optimised, and which stream is it in*. **Read it
before naming ANY strategy, family or batch as work to start.** L802 records the miss it exists to
prevent: a ranking built from the strategies' properties and none of the ledger's recommended a
family that was already finished.

**Columns** - strategy, family (the category the strategy declares in its own `_strat` / `_strat3`
call), R5 fires, projected Step-1 fires, changed-since-R5, survives_pct, STREAM, ticket, status -
one of EIGHT, mutually exclusive (B2825/B2833): five terminal (DONE-ADMITTED / DISABLED /
PRUNED-DUPLICATE / CLOSED-NEGATIVE / CONTAINED-IN-REPRESENTATIVE) and three in lanes (IN-CAMPAIGN /
STALLED-CAMPAIGN / NOT-STARTED).

**STREAM is the optimisation lane, and the rule is mechanical:**

| stream | meaning | cost |
|---|---|---|
| `TIGHTEN` | a persisted magnitude can be tightened, so every level is a SUBSET of the recorded fires | ZERO engine hours (§3) |
| `LOOSEN` | fire-starved at the current condition - the productive direction is a WIDER producer band | ENGINE resim; a looser level admits bars the cube never recorded (§4) |
| `BOTH` | tightenable AND fire-starved | offline first, engine after |
| `NONE` | no numeric knob and not starved | a BREADTH candidate (§3.6) |

**COUNTS LIVE IN THE STAMPED VIEW, NEVER HERE (B2829; the L639 fix by construction):** this section
stopped quoting live totals after three builds in two days each left a stale snapshot in prose.
Trust ONLY a copy whose L803 build stamp matches HEAD - if it does not, REGENERATE FIRST and commit
the fresh build. What this section owns is the INVARIANTS, which do not rot: the eight statuses
partition all registered strategies exactly; terminal statuses are mutually exclusive with every
work lane; IN-CAMPAIGN requires a campaign-vocabulary ticket whose CURRENT ledger state is
non-terminal (B2829 - a concluded campaign does not own a strategy forever); a row whose campaign
tickets exist but are ALL terminal is STALLED-CAMPAIGN (B2833, owner-approved 2026-09-15) -
campaigned, concluded mid-path, KEEPS its stream lane and its workflow eligibility; the lanes
classify on the CURRENT-GATE projection (raw x survives); and `reopen_candidate` FLAGS a terminal
row whose entry condition moved since its closure evidence - reopening is the OWNER'S word, never
automatic. Per-family tightening-candidate counts are programme state, recorded in the campaign log.

**Four caveats bound every number in it, and are printed in the file itself:** `changed_since_r5`
is an UPPER bound (any code difference counts, including a rename); `stream = TIGHTEN` rests on a
source pattern for numeric comparisons and is a LOWER bound (a threshold reached through a helper
or compared to a config constant is invisible to it); `survives_pct` calls the LIVE strategy
function on each fire's persisted signals (S6-B2814; `-` only for zero-fire strategies) and is a
LOWER bound where a gate leg reads an unpersisted key; and `IN-CAMPAIGN` requires a
campaign-vocabulary token in the row naming the strategy (S6-B2810c - a bare mention is not a
campaign), a HEURISTIC with measured misses in both directions, so a borderline row is settled by
reading the ticket and the JSON's `mention_tickets` keeps the unfiltered list. `STALLED-CAMPAIGN`
inherits this heuristic WITHOUT the B2829 liveness mask, so a builder-audit ticket naming a strategy
as an example can stall it falsely (9 of 46 at the B2833 build; disclosed in both artifacts,
exclusion awaiting the owner's word).

## 1. GOVERNING RULES - bind both workflows

### 1.1 HOLDOUT POLICY - settled by owner 2026-08-09 (formerly §0 and §1)

**RULING: the holdout window is LOCKED to R5's dates, `2025-05-05 -> 2026-05-05`, 1 year,
unchanged.** Owner: *"We do not change the dates and duration of the holdout period. they remain
the same as in r5. this is to ensure comparibility. No logic changing that even if its been graded
9 times on pre-optimized gates."* Option A (re-partition) is REJECTED; Option B (extend forward) is
unavailable. Moving the holdout would make the optimised roster incomparable to the R5 baseline and
to every measurement since. **Comparability is the point of a fixed holdout, and it outranks the
marginal statistical benefit of a fresher one.**

**Option C is the operative design, and does not conflict with the ruling:** it governs how many
TIMES the fixed window is read, never where it sits - the holdout is read only at the end, on the
final pre-registered candidate set (item 1 states how many reads each path spends), and all
intermediate optimisation happens in-sample. The governing constraints:

1. **The holdout is read only at Step 2, on the final pre-registered candidate set** - ONE read for
   an offline campaign (§3.4 F5), and under the engine waterfall one read per slate config for the
   strategy under test, stopping at the first qualifier (§4.8: *"Each config spends an IRREVERSIBLE
   read of the locked holdout year"*). Never per iteration, never to "check how it's going". After a
   read the holdout is SPENT for those objects (B2136): a ranking re-derived afterwards is a
   candidate, never a verdict. *(Reconciled at B3096, not ruled: the B1497 wording read "ONCE per
   phase, at the end ... Not per strategy", written for the two-phase design B2828 superseded; the
   later waterfall ruling (owner 2026-08-29) spends one read per config per strategy, and the two
   texts had stood side by side unreconciled.)*
2. **Pre-registration.** The search space - which signals, which thresholds, which objective - is
   written to `EXECUTION_QUEUE.md` and committed BEFORE any score is computed, and the Step-2 cell
   is committed BEFORE any holdout code path runs (the ordering IS the pre-registration). A grid
   chosen after seeing results is not a grid, it is a story.
3. **Selection statistics never touch the grading window.** Selection happens in-sample and the
   holdout decides; a maximum over many configs on the graded window almost always "passes" and the
   number means nothing (the B1452 retraction; the B1454 de-dup correction was a milder instance).
   The mechanisms are code-level and testable: `select_exit` slices `in_sample()` ITSELF, so the
   EXIT choice cannot see the holdout (`roster_core.py:345-357`, pinned by
   `test_b1800_step1_exit_selection_is_is_only` - a holdout-only frame yields NO exit, with a live
   control proving the fixture can select), and Step 1 ranks on `is_sharpe` / `is_ci_lo`, never the
   holdout key (B1718 P0-2, owner-approved). **A claimed mechanism that does not exist is worse
   than an acknowledged gap** (B1820 / S6-B1705c, owner: *"major and unforgivable"* - a "file path containing IS rows only" was
   promised and never existed; the grader is handed the full cube and slices it itself).
4. **Every reported number ships with its diagnostics** - sensitivity curve, leave-one-out
   contribution, churn (in/out), and effective breadth (CHECKLIST #175, #176).
5. **There is NO usable prior for a strategy's optimisation outcome** (owner correction
   2026-08-09: *"The R6b prior is the base rate - this is incorrect especially for the untouched
   strategies."*). R6b was a LOOSENING experiment on already-examined strategies; a different
   operation on a different population is not a base rate. Earlier results are motivation for the
   discipline, never a numerical expectation.
6. **The prior holdout reads were small spends** (moderating L351). They calibrated a handful of
   GLOBAL gate parameters (~3-5 distinct gate configurations - Sharpe 0.5 -> 1.0, `min_trades`
   levels), not strategy-specific configs, and the Sharpe bar was chosen on principle from a
   sensitivity curve presented before the choice. L351 stands as a discipline (count holdout reads
   project-wide) with its magnitude corrected.

only on an owner ruling - the hash change is then visible to every artifact run under it.

| phase | scope | window | universe | produces |
|---|---|---|---|---|
| **0 INVENTORY** | build the SPECS entry | — | — | formula + Table A + factorial |
| **1 SEARCH** | all fire-adding configs | **1 year, 2024-05..2025-05** | **200** | ranked combinations |
| **2 VALIDATE** | **top 3 CONFIGS (owner 2026-08-29 second set; was top 5 same day, top 10 combinations before)** | **4 years, `2022-05-05 -> 2026-05-05` (owner 2026-08-29: 2022-23 allowed for Step 2)** | **ALL 544 (owner 2026-08-29; was 344 disjoint)** | gate verdicts |

that cannot be typed needs no rule about typing it right).

- **Step 1 runs 1 year, `2024-05-05 -> 2025-05-05`, ending exactly at the holdout boundary**
  (owner ruling 2026-08-21). Running it to `2026-05-05` meant ranking on the holdout year Step 2
  judges (`S6-B1605c`). **STEP-1 SHAPE IS GATE-ENFORCED (B2711, owner-caught 2026-09-12):**
  `producer_variant_table._step1_shape_refusals`, called inside `launch_refusals`, refuses (a) ANY
  Step-1 window reaching past the IS/HO boundary - absolute, no waiver buys it, because such a
  search ranks combinations on holdout data and spends the family's pre-registration - and (b) any
  other deviation from the ruled window or the ruled 200-ticker universe carrying no
  `step1_shape_waiver` that quotes the owner. Incident: a pilot was specced at Step 2's 4-year
  window and killed at sim-day 45 (L787 / CHECKLIST #301; pin `test_b2711` uses that spec as its

- **Why 200 tickers (B1817, measured; owner ruling 2026-08-21).** Three standing constraints -
  holdout locked, no 2022-23 data in Step 1, Step 1 off the holdout - admit no window with enough
  sample at 100 tickers: a 1-year window alone kept only 50-56 pct of entries on the cubes it was

  and the UNIVERSE is the lever: 100 -> 200 (`S6-B1696c` option (a)). In ticker-years the change is
  approximately neutral - 100 tickers x 2 years and 200 tickers x 1 year are both 200 ticker-years -
  but not exactly: warmup and per-run fixed costs are not linear (`S6-B1831b`).
  A 200-ticker Step-1 window was measured to fire on 29 of 29 screen-days - the surviving half of the
  B1861 note, which B1877 otherwise retracted.
- **No 2022-23 data in Step 1 (owner 2026-08-17)** - the market changed materially with AI adoption,
  so 2022-23 is not wanted even for exit selection. **SUPERSEDED FOR STEP 2 ONLY (owner 2026-08-29):
  Steps 2 and 3 run the FULL 4 years `2022-05-05 -> 2026-05-05`**, which is what the full-period
  trade floor is measured over; this resolved the three-way conflict recorded at S6-B2358.
- **Step 2 universe = ALL 544 tickers, graded across the full in-sample AND holdout window** (owner
  2026-08-29; supersedes the 344-disjoint design, and the older 100-search / 444-validate split).
  It includes the 200 Step 1 selected on, so Step 2 is not cross-sectionally disjoint: its
  out-of-sample content is the LOCKED HOLDOUT YEAR plus the 344 tickers Step 1 never saw. The deeper
  544-ticker base is what makes the trade floors meaningful. **Accepted limitation:** nothing tests
  whether an edge survives a regime change.
- **THE BASELINE UNIVERSE IS 544 (B1618, owner 2026-08-17)** - `output_audit/r5_universe_544.txt`,
  from the R5 baseline cube (`output_r5_merged_1_7`, 544 tickers, 25 pct A-C, mega-caps present).
  NOT the former `r5_universe_381.txt`, an abandoned alphabetically-partitioned chunk (380 of 381
  tickers A-C, no mega-caps, 248 tickers R5 never ran - L445), which the sweep BUILDER still read
  until it was repointed (L479, CHECKLIST #199). **Derive a universe from the BASELINE ARTIFACT,
  never a roster CSV** (L378), and characterise any ticker file before use (#187 / #193; §4.5 Step
  1.0).
- **Step 1 produces a RANKING, not verdicts.** Step-1 admission is min-trades >= 10 plus a ranked
  list with NO gates (owner ruling B1608); gates are Step 2's. Every Step-1 `holdout_n` is 0 by
  construction - the window ends at `HO_START`, so `roster_core.holdout()` returns an empty frame -
  and `PASS: 0, FAIL: 0` across a Step-1 grid is a STRUCTURAL fact about the window, never a quality
  verdict. If Step 1 ever produces a PASS it is doing Step 2's job (L471). `full_period_n` IS
  populated at Step 1 (over its 200 ticker-years), which is what the Step-2 pre-triage projects
  (§4.8).

### 1.5 RESIMULATION - the rule is SUBSET-SAFETY, not "tightening" (B1508; formerly §2.1, §2.3a and §0a item 1)

`trade_log.csv` carries `signals_at_entry`: the complete producer signal dict at the entry bar
(~22 KB per trade, verified B1497). Therefore TIGHTENING is exact and free where it only selects a
subset of trades that already exist with known outcomes, and LOOSENING is impossible offline - a
looser threshold admits trades that were never generated. The correct criterion is whether a
parameter can only REMOVE fires or can also ADD them:

| | parameter class | cube-gradable? | why |
|---|---|---|---|
| ✅ | **SUBSET-SAFE** - can only REMOVE fires | **YES, free and exact** | every surviving trade already exists in the cube under every registered exit, so grading is a lookup |
| 🔴 | **FIRE-ADDING** - can change WHICH bars fire | **NO - needs the engine** | produces `(ticker, date)` pairs the cube never took; the cube holds no P&L for them |

A parameter that can ADD fires (a producer lookback that rebuilds the event set, an EMA `span` swap) produces trades R5 never took, and the cube holds no P&L for those.
A parameter is fire-adding whenever it changes the producer's own detection or swaps one leg of the
gate for a different signal. **Neither is "loosening" in the ordinary sense, and both were
mis-classified as free under the original wording** - the original answer, *"tightening never
needs the engine"*, was too broad. VERIFIED B1499: every sampled
`(ticker, entry_date)` trade (202 of 202) carries one `exit_method` row per registered exit, so the
subset-safe half is genuinely exact - the best exit CAN change when the population changes and is
re-selected in-sample, but no simulation is involved.

- **The discriminator is PERSISTENCE, not monotonicity (L726).** Classify every parameter against
  `signals_at_entry` before any launch: a persisted magnitude is FREE on its tighter side; a
  producer-internal parameter is ENGINE. The schema carries it as `free_band` / `resim_band`.
- **Engine runs = the product of the FIRE-ADDING bands alone (L371);** every subset-safe combination
  then derives offline from each run. MEASURED on the first campaign: 4,000 combinations needed 20
  engine runs - costing by combinations overstated the workload 200x.
- **Carrying an equivalence class is free - for SUBSET-SAFE parameters only** (formerly battery step
  6b). MEASURED on one 420-fire cube: a FIXED diagnosis of 3.5 s shared by all combinations and
  0.01-0.03 s marginal per combination graded, so carrying 21 combinations instead of 10 costs
  ~0.2 s; the real cost is the single ENGINE RUN that produced the cube. **The calculus INVERTS for
  a FIRE-ADDING parameter:** each distinct value needs its OWN engine run, so a fire-adding parameter
  must never be carried as an equivalence class - its values are the CONFIGS of the sweep, decided
  before launch and capped by budget. If a fire-adding parameter is ever added to the graded grid,
  this bullet stops applying and the carry must be capped explicitly.
- **A subset of SIGNALS is not a subset of TRADES (L812).** The engine blocks a fire while the same
  strategy holds that ticker (`backtest.py:2795`, `open_combos`), so a tighter level FREES occupancy
  and can admit trades present in no cube: every offline trade count is a LOWER BOUND and offline
  verdicts are candidates. B2905 made the per-strategy occupancy count measurable in every cube
  written after it. Separately, the candidate cap cannot truncate: under `--cube-isolation`
  `backtest.py:2442` bypasses `max_candidates_per_day` (R5's cap bound on only 1 of 972 days, and
  isolation ignores it entirely), which is what makes subsetting exact for the cap (L645: the objection costed and void) - re-checked per strategy, and disclosed when a cube
  offers no evidence either way.
- **Site the baseline at the LOOSEST admissible level of every persisted gate** where the strategy
  has one, so a single cube contains every tightening as a subset (§4.4 item 3).

### 1.6 Family campaigns - pre-gate, representative, sibling pass, run producers once (B2627-B2633; formerly RUN-PRODUCERS-ONCE and the programme-state family reading)

**The campaign unit is the FAMILY, not the registration.** Collinear strategies share most of their
trades - one family measured 20 registrations collapsing to about 1.2 independent bets. So:

1. **PRE-GATE before any campaign target is picked** (council verdict S6-B2627;
   `scripts/family_pregate.py`): trade overlap + band clustering + the MEDIAN-exit holdout printed
   beside the best-cell key (the best-vs-median gap is selection inflation, on the artifact's face).
   A family is CONFIRMED or SPLIT only by this measured overlap, never by a name prefix.
2. **Pick ONE representative** per cluster, with the criterion stated (#165).
3. **Close the rest by a PRE-REGISTERED sibling containment pass** after the representative's
   verdict (the pre-registration committed BEFORE grading; each sibling's overlap recorded), so
   siblings ride the verdict instead of getting campaigns. A contained sibling that grades BETTER
   than its representative gets its OWN pre-registered Step 2, not a dismissal: containment bars a
   second independent BET, not a better strategy (L775). Where that sibling's winning cell was found
   on the already-read holdout, the cell is FORWARD pre-registered - committed before any
   post-holdout data exists - and gets ONE six-gate read on the first cube spanning at least 12
   forward months; qualify goes to the roster, anything else closes the strategy FAIL with no re-pick
   (owner ruling 2026-09-09; the holdout is never re-read, B2136; the first instance is in the
   campaign log).
4. **No engine campaigns on collinear siblings** (council verdict, S6-B2627) - a compute-economy
   rule, which does not apply to a zero-engine-hour campaign (L775).

**RUN PRODUCERS ONCE, REUSE THE DATA (owner directive 2026-09-07, B2633).** Three reuse layers,
standing policy for every family campaign:

1. **Producer layer:** every producer precompute for a config is built ONCE into a tagged cache
   through ONE shared dir-resolver imported by producer AND consumer (the S6-B2484 pattern;
   `build_params.json` provenance per B2622), and every family member reads the same artifact. A
   missing tagged cache falls back to the untagged production artifact and runs a silent duplicate
   of the baseline, so assert every tagged precompute exists before launch (on-ramp R9).
2. **Engine layer:** an engine run carries the family - every OPEN consumer of the knob it varies -
   in `strategy_subset` (ADMITTED strategies are excluded, since the launch gate refuses them - B2731,
   banked lines are closed - and so is every B2825 terminal status): the engine computes every strategy's signals per bar anyway, so the marginal
   cost of the siblings is near zero and ONE run lands a cube for every member at that config
   (§4.3).
3. **Offline layer:** everything downstream of a landed cube is RE-SCORED, never re-run - free
   levels (B2569), sibling grades (the pre-registered pass), tightening subsets, and the pre-gate
   itself all read cubes already on disk.

**A knob read by several strategies moves all of them.** Its consumer list is MEASURED from the tree
(`producer_variant_table.knob_consumers`, B2579) and pinned equal to the declaration; in an
optimisation run every consumer in the subset is graded as a variant (§4.3). The risk it guards
(MEASURED B1617): harmless while a run carries one strategy under `--cube-isolation`, but in a
full-roster run a knob tuned for one consumer silently retunes the others. The first family's
resolution (S6-B1617b, owner-approved) ships a tuned line as SUFFIXED variant keys bound to their
own strategy, leaving the base keys and the roster untouched until an admission is approved.

### 2.3 ACTUATION - A BAND WHOSE PARAMETER DOES NOT EXIST IS NOT A BAND (B2866, owner-directed 2026-09-19; formerly §11.0b)

name - the L751 class, where a flag accepted, stamped into the artifact and never applied is worse

### 2.5 Strategies whose entry condition moved after R5 - the survival check (B2806, owner-directed 2026-09-13; formerly §11.2b4)

**Why it exists.** R5 (`output_r5_merged_1_7`, trade_log dated 2026-07-24) is the comparison basis for
every offline read. A strategy's ENTRY CONDITION - the boolean in `screener.py` deciding whether it
fires on a bar - may have been edited since. Where it was, R5 records a population the current
condition would NOT produce, and any figure read off those rows describes a strategy that no longer
exists in that form. The status view's `changed_since_r5` column marks them (an AST-diff of every
`strat_*` function between the R5-era screener commit `fee970996` and HEAD). **It is an UPPER bound on
behavioural change:** any code difference counts, so a rename or a configurable-span swap that is
identical at its default is included beside real tightenings. The measured list, its examples, and
the roster-exposure check are in the campaign log.

**The rule - it is the Step-0.6 check made concrete.** Before reading any R5 figure for a strategy -
changed or not; the section measured an unchanged one too - re-evaluate its CURRENT condition against the persisted `signals_at_entry` of its recorded
fires and state the survival rate (W-T step T1). The result goes in the spec `note` and the queue row.
**A LOW SURVIVAL RATE IS NOT A VERDICT ON THE STRATEGY (owner ruling 2026-09-13, verbatim in the
campaign log):** it is a question of varying thresholds within producers - loosening included - and
that qualifies the strategy for optimisation. The OFFLINE path is tightening-only BY CONSTRUCTION, but
the ENGINE has no such limit, and DEPTH over all producer bands INCLUDING loosening is Priority 1
(§0.3). So a strategy whose entry condition moved is NOT disqualified and NOT trusted on its R5
numbers: it gets the survival check first, and where the current condition is rare, the LOOSENING
half of its producer bands is scheduled as an engine depth sweep (W-L) rather than treated as a dead
end. Two LOWER bounds, for different reasons: a survival rate is a lower bound where a gate leg
reads a key the cube did not persist (S6-B2814); and a projected fire GAIN under a looser or new
condition is a lower bound because a bar that satisfies it but never fired under the old gate is
absent from the cube (S6-B2810d).

### 2.6 Step 0.6 - the offline-or-engine branch, per level (formerly §11.2 step 0.6)

For each parameter, ask whether the MAGNITUDE it thresholds was persisted in `signals_at_entry` at
fire time. If EVERY scheduled level tightens a persisted magnitude, Step 1 needs NO engine run - go to

### 4.3 SHARED-PRODUCER RESIM REUSE - why the full consumer set is FORCED (B2707 owner philosophy; B2828 mechanics; formerly §11.2s)

Owner philosophy, verbatim 2026-09-12: *"we will do a resim and re use the data for shared producer fot
offline cube generation"*. A producer-band resim is a FAMILY asset, never a one-strategy expense: a
producer knob is GLOBAL, so one variant config recomputes every signal that producer emits, and every
strategy whose gate reads them fires against the variant in the same run.

**The physical constraint that decides the design:** `signals_at_entry` persists ONLY on trades
actually taken. A variant cube run with `strategy_subset = {X}` records nothing for X's siblings - there
are no rows to grade. So reuse is not an optimisation bolted on afterwards; it is only possible if the
resim run INCLUDES every strategy that should later read the cube. Hence the rule (the B2707 doctrine,
generalised to every family):

1. **CONSUMER SET, measured not asserted:** a producer-reach map lists which strategies' gate keys
   derive from the producer's outputs, committed as an artifact
   (`output_audit/<batch>_<family>_producer_map.json`). A family without one BUILDS it at L0 - gate keys
   per strategy grepped against the producer's emitted keys. `knob_consumers` proves the env knob's
   file-level blast radius; the reach map narrows it to strategies. **A knob's reach is MEASURED, not
   assumed (B2735):** a producer parameter feeds only the primitives that take it, so strategies whose
   keys come from parameter-independent sources need their OWN axis.
2. **OPEN consumers only:** the subset excludes ADMITTED strategies (the launch gate refuses them -
   B2731, banked lines are closed; §1.3) and every B2825 terminal status (§0.7).
3. **ONE run, N gradings:** the spec's `strategy_subset` file lists the full open consumer set
   (riders per B2710 where cube-only members apply), carries the variant identity in the cube dir name
   and the manifest, and persists `signals_at_entry` as standard; every consumer's Step-1 grading then
   reads the SAME landed cube offline (L6). The leverage line divides engine hours by the open-consumer
   count, so the true per-strategy cost is what the owner sees.
4. **The registry closes the loop:** every landed variant cube's manifest carries the knob identity;
   L2's lookup scans manifests BEFORE proposing hours, so a level another family already paid for is
   never bought twice. The band-coverage gate accepts these cubes as resim evidence via
   `resim_configs` / `--resim-evidence`.

**STATED ASSUMPTIONS (none silent - each traceable to a ruling):** windows are the ruled shapes (Step 1
200 tickers x 1 year; Steps 2-3 4 years x 544; §1.2); IN-CAMPAIGN rows belong to their tickets;

### 4.6 Step 1 grading (formerly §11 STEP 2 GRADE)

**Grading is family-dispatched.** The battery runs the family grader (`tools.grade`) on every landing
at the manifest's own parameters (§5, B2520), so a hand re-grade is the exception and uses the same
grader (each family's command is in the campaign log). The first family's grader, per combination,
filters the cube to the surviving fires, selects the best exit **IN-SAMPLE ONLY**, grades the holdout on
the six gates via `roster_core` (the identical bar to the Phase 1B roster) and records all 15 metrics
(§7.3); on a Step-1 cube the holdout is empty by construction (§1.2), so the gate half only bites on a
Step-2 cube. Later graders follow the same `roster_core` path, each stating its method in its own
header - one reads the holdout ONLY on a cube declared Step 2.

**Verdicts:** `PASS` · `FAIL` · `BELOW_POWER_FLOOR` (holdout n below the grader's `--min-n`, default 10 - NOT `min_trades_holdout`) · `NO_EXIT_SELECTABLE` (too few IS trades to rank the registered exits - a SAMPLE-SIZE verdict, not exit quality) · `ZERO_FIRES`.

**The power floor is not a gate and is not `min_trades_holdout`** (S6-B2353 and its own correction both
got this wrong; pinned by `test_b2362`). BELOW_POWER_FLOOR is the EARLY RETURN in `roster_core.evaluate`
(`roster_core.py:215`, `if n < min_n: return None`), taken BEFORE any gate is computed, with `min_n` from
the grader's `--min-n`; `min_trades_holdout >= 15` is one of the six LIVE_GATES, evaluated only for
cells that already cleared the floor. **EXECUTED probe at `--min-n 10`:** n=8 -> None; n=10 and n=12 ->
GRADED with `min_trades_holdout=False`; n=15 -> GRADED with it True. So a cell with 10-14 holdout trades
IS graded and FAILS the holdout gate; below 10 it is never graded at all. Two cuts, two numbers, both
live.


### 4.7 THE MECHANICAL TOP-3 CONFIG SELECTION - the Step-2 slate (owner ruling 2026-08-29; formerly STEP 2 ENTRY)

Step 2's unit of execution is the CONFIG (one holdout cube per config); its unit of evidence is the
graded cell. The older top-10-combinations spec is superseded: **the top 3 CONFIGS advance**, selected
by this mechanical process - no judgement calls, reproducible from the grid artifacts. Run it only
when EVERY Step-1 spec of the campaign is COMPLETE, and record the top-3 list, each with its
`is_ci_lo`, in the queue row:

1. For every graded config, take `step1_ranking[0].is_ci_lo` - the best distinct combination the config
   produced (the ranking is already equivalence-class collapsed).
2. Rank configs descending on that value.
3. **Duplicate-signature collapse:** if a config's best row carries the same (is_ci_lo, is_sharpe,
   fires, exit) signature as a HIGHER-ranked config's best row (Table D's `dup` column), it is the same
   discovery - skip it and continue down the list. **ALL ordering ties** - equal `is_ci_lo` across
   different signatures at item 2, or tied signatures here - **resolve deterministically, by a tie-break
   the campaign records before ranking** (the first campaign broke ties to the LOWEST value of its
   fire-adding axis, a later one to the lower config index - both in the campaign log); never by sort
   order, since without a rule the holder is sort-order-dependent, which a verification run caught
   before the rule shipped.
4. Take the first **3** survivors (owner ruling 2026-08-29 second set, was 5 - a 5-config slate
   projected ~92 h serial at the 4-year span, judged too long for the execution timeline).

**READ THE TIER BEFORE THE RANK.** The slate is ranked on a lower bound, which still favours a tight
small sample over a noisy deep one. Table D carries each row's IS n and tier beside the sort key for
exactly this reason (RANK IS NOT TRUSTWORTHINESS, §7.5) - read them before the rank; a recorded slate's
leader was its SHALLOWEST member (campaign log).

**COST - projected PER CONFIG from its OWN Step-1 base, never from the median (S6-B2364).** Scale each
config's measured Step-1 duration by Step-2 ticker-years over Step-1 ticker-years (544 x 4 / 200 x 1 =
**10.88x**). Step-1 durations at identical ticker-years have measured a 3x spread, so runtime is NOT
purely ticker-year-driven, and a median-scaled figure is wrong for a SELECTED slate because
selection on `is_ci_lo` is not independent of runtime (on the first campaign the median-based figure
understated the slate by ~25 h; campaign log) (the L708 shape: a statistic computed over a
population and applied to a selected subset). It stays an ESTIMATE until the first cube lands. Each
campaign's slate and cost table are recorded in `STRATEGY_CAMPAIGN_LOG.md`.

### 4.8 THE WATERFALL - Step 2 execution (owner ruling 2026-08-29, third set; formerly STEP 2 EXECUTION, DECISIONS RULED, STEP 2 PRE-TRIAGE and STEP 3 VALIDATE)

**Owner, verbatim:** *"Lets do a waterfall method. If any of the 300 combinations from config 1 qualify
for phase 1B after clearing all gates we do not run the next two configs else we continue to config 2
then 3 then terminate."* The ruling's "300 combinations" is the campaign it was ruled on; the RULE is
family-general (B3089). `<C1>`, `<C2>`, `<C3>` are the slate from §4.7; `<K>` is the number of graded
cells the family's grid carries per config - **"every graded cell the config produced", which is
family-specific**; `<STRATEGY>` is the strategy under test. Configs run SEQUENTIALLY in the mechanical
rank order, and after each config's cube is graded all `<K>` of its cells are evaluated:

1. **Config 1 = `<C1>`.** Run it **IN ITS ENTIRETY** - all `<K>` cells graded; the waterfall never stops mid-config. If any cell qualifies -> **STOP. Configs 2 and 3 are not run.**
2. Otherwise **config 2 = `<C2>`**, in its entirety. If any qualifies -> STOP.
3. Otherwise **config 3 = `<C3>`**, in its entirety. If any qualifies -> admit it; otherwise **TERMINATE** - `<STRATEGY>` closes NEGATIVE for Phase 1B and the programme moves to the next of the optimisation backlog.

**WHY THE SEQUENCE IS NOT OPTIONAL.** Each config spends an IRREVERSIBLE read of the locked holdout year
for `<STRATEGY>`. Launching the slate in parallel, or "launching the top 3" as one batch, spends reads
the waterfall exists to protect. **A request to launch Step 2 for the top 3 configs is executed by
launching config 1 and reporting its verdict**; configs 2 and 3 are conditional on that verdict by
construction.

**WHAT "QUALIFY" MEANS, IN CODE.** A row gets `verdict = "PASS"` iff `all(gates.values())` over the six
`roster_core.LIVE_GATES` (`roster_core.py:60-61`: pooled_sharpe, profit_factor, sortino, psr,
min_trades_holdout, min_trades_full_period). Anything returning `None` from `evaluate` never reaches the
gate branch at all and is `BELOW_POWER_FLOOR` (§4.6). **Qualification is that PASS, full stop.**

**THE 2026-08-30 AMENDMENT (S6-B2409), owner verbatim:** *"noise floor is 0.333 meaning that the result
has to be more than 1.333 in the holdout period to qualify. Remove the 0.333 selection-noise floor
requirement in its entirety."* The original D1 stop condition was *qualifies AND is ROBUST* (holdout
Sharpe above 1.0 + 0.333); the owner retired that floor and the ROBUST/PROVISIONAL split in their
entirety, so clearing the six gates IS qualification and IS the stop condition. In code
`roster_core.robust_status` became `roster_core.qualifier_margin` (the margin over the live pooled gate
as a plain number - no floor argument, no label); `SELECTION_NOISE_FLOOR` was deleted from the roster
builder; the grid payload's `provisional_qualifiers` key became `qualifiers` (every PASS row); the
renderers no longer frame any value against a floor; pinned removed by
`test_b2409_floor_retired_margin_measures_live_gate`. The prior recommendation of the floor as the
grid-stage selection-noise control is recorded as overruled (L633 - stated once; the ruling governs).

**WHAT THE WATERFALL MAKES LOAD-BEARING.** Under a ranked list a marginal winner is one row among many
the reader judges; under first-success-wins it ENDS the campaign's Step 2. That is why the decisions
below had to be ruled before the first launch rather than judged after it.

**DECISIONS RULED - ALL SIX (owner, 2026-08-29, S6-B2375; amended 2026-08-30) - class-level form; each
decision's verbatim wording and the campaign it was ruled on are in the campaign log:**

| # | ruling |
|---|---|
| D1 | A config RUNS TO COMPLETION before the stop test. Its original second half - stop only on a ROBUST qualifier - was retired 2026-08-30 (above): the stop condition is bare PASS, and with the ROBUST hurdle gone `psr >= 0.95` is the remaining significance-style control on a qualifier. |
| D2 | No multiplicity correction across a config's graded cells (§1.4); if several qualify, D3 decides. The recommendation of the opposite is recorded as overruled (L633). |
| D3 | Where several cells qualify, the highest **HOLDOUT pooled Sharpe** advances - the gated quantity (`roster_core` `pooled_sharpe`), not the in-sample `is_sharpe` Step 1 ranked on. |
| D4 | The waterfall supersedes the ranked-list goal recorded at S6-B2242 (*"We decide based on over all ranked list. That itself is the goal of step 2."*) for Step 2 only: it is a FIRST-SUCCESS stopping rule, so when config 1 qualifies no cross-config ranking will exist - a coherent but DIFFERENT goal ("find one that clears", not "pick the best"), stated rather than applied silently (L633). |
| D5 | Order is the mechanical rank order (§4.7). |
| D6 | If all three fail, the strategy closes NEGATIVE and the programme moves to the next of the backlog. **The METHOD is not on trial** - the negative result is evidence about that strategy (§1.8). |

**Consequence resolved by the same ruling:** a campaign terminating NEGATIVE while holding a
gate-clearing cell can no longer occur - a gate-clearing cell now stops the waterfall itself.

**STEP-2 PRE-TRIAGE - MANDATORY BEFORE ANY STEP-2 CUBE, PER CAMPAIGN (S6-B2369; B3089).** Not a one-time step: it projects THIS
family's Step-1 `full_period_n` past the trade floors, so a run recorded for one strategy says nothing
about another. **The method (it superseded a `measure_fire_count.py` step approved earlier the same day,
which swept only 2 of 6 config axes and counted ENTRY fires, an upper bound):** the Step-1 grids already
carry `full_period_n` PER COMBINATION for the exit each selected, across every axis - a strictly better
instrument requiring no engine run. **The projection:** Step-1 scope 200 ticker-years; Step-2 full period
544 x 4 = 2,176 (**10.88x**) and Step-2 holdout 544 x 1 = 544 (**2.72x**); a combination needs Step-1
`full_period_n` > 75 / 10.88 ≈ 6.9 for the full-period floor and > 15 / 2.72 ≈ 5.5 for the holdout
floor, so **the full-period bar binds**. Record each slate member's worst per-cell projection.
**LIMITATION, stated so the projection is not over-read:** it assumes the Step-1 fire rate holds across
2022-2026, and no Step-1 config runs a day of 2022-23, so the rate in the added years is UNMEASURED
(2022 in particular was a distinct regime). Each campaign's pre-triage result is recorded in
`STRATEGY_CAMPAIGN_LOG.md`; where every combination projects past both floors, the four STATISTICAL gates

**COST PROFILE.** Best case: config 1's cost alone. Worst case: all three. The waterfall is never more
expensive than the flat top-3 slate and usually cheaper.

**NO separate baseline run (L423).** All six gates are ABSOLUTE thresholds, so admission depends on a

#### Step 2.2 - THE SPEC, and the one field that is easy to get wrong

This is the FAMILY-NEUTRAL shape the launch gates accept. Copy the SHAPE; take every value from your
own family's SPECS entry and campaign record, never from another family's spec (each launched
instance is recorded in the campaign log).

```json
{"wave": "<campaign>_<config>_step2",
 "strategy_subset": "output_audit/_subset_<strategy>.txt",
 "step": 2,
 "step1_cube": false,
 "leg_cap_hours": 4.5, "max_legs": 10,
 "pool_workers": 6,
 "allow_engine_drift": true,
 "resume": true,
 "fires_at_production": "<the family step-0.5 smoke count at production params>",
 "arms": [{"tag": "step2_<config>",
           "env": {"<FAMILY_KNOB>": "<config value>"}}]}
```

- **`step1_cube: false` - set it explicitly, and know what it reaches.** A Step-1 marking arms the
  **holdout-touch FAIL** in run_postconfig - correct for a Step-1 search, which must not touch the
  holdout, and **WRONG for Step 2, which grades ON the holdout by design.** The spec field selects the
  step only for run_wave's own post-landing call (`run_wave.py:374`, default TRUE). On a real engine
  landing that call is a no-op: the engine hook lands the cube first with NO step flag, and
  `run_postconfig.derive_step` takes the step from the manifest window, where a window ending after
  HO_START is Step 2 (`run_postconfig.py:398-417`; `postconfig_landing.py:451-457`). So a copied Step-1
  spec arms the failing check only on the FALLBACK path, where run_wave's call is the landing. (The
  pre-B3096 text said a copied Step-1 spec arms a check guaranteed to fail; that holds only on the
  fallback path.)
- **The config axes are ENV, not CLI flags** - each family's knobs are read from the environment in
  `backtest/config.py`, and run_wave passes each arm's env dict to the engine (`run_wave.py:291`).
  Which variables a family has is in its SPECS entry, never in this template.
- **The window and the universe are NOT typed in the spec** - `phase_table.resolve(2)` injects the full
  4 years (`2022-05-05 -> 2026-05-05`) and the 544-ticker universe (§1.2), and `spec_refusals` refuses a
  typed window (B2713 / L788).
- **`fires_at_production` is required** - run_wave carries it into the generated manifest and the
  prelaunch gate refuses a launch without it (S6-B2848c).
- **`resume: true` is harmless on a fresh directory** (`run_wave.py:269-271` resumes only when
  `engine_state.json` exists) and makes a relaunch continue from its checkpoint, not restart.
- **`leg_cap_hours x max_legs` is the capacity** and must exceed the projection; the leg cap stays
  under the owner's 5 h ceiling (4.5 here leaves margin under it). A resumed invocation's leg counter
  restarts at 1. `pool_workers` 6 is the value the first pooled Step-2 wave was relaunched at after its
  commit exhaustion (campaign log; Step 2.4) - a starting point, not a measured optimum. Size it on the
  commit reading of Step 1.0 (b), since commit is the binding quantity (L670).

#### Step 2.3 - MEASURED RUNTIME - per campaign and per pool size, never carried from another family's run

Take it from the run's own `[B2127 rate]` line at the first leg boundary; until then use the family's
Step-1 rate scaled by §4.7 as a labelled estimate. The window is 1,003 NYSE trading days (nyse_mcal).
**The first rate line of a RESUMED invocation is mis-scaled:** run_wave starts its per-invocation
sim-day counter at 0 (`run_wave.py:242`, used at `:87`), so the first leg of a resumed invocation
divides its hours by every sim-day since day 0; compute the true rate as leg seconds / sim-days that leg
advanced until S6-B3094a ships. Each campaign's measured rate and memory readings are recorded in

#### Step 2.4 - THE MEMORY CEILING - three rules, each of which cost something to learn

- **A pyramid alongside a live wave is not free.** A pooled engine alone has run at tens of GB of
  commit, and engine plus a pytest run has reached commit exhaustion - the class S6-B2237 records as
  having killed three prior runs. Do not run the full suite against a live wave. **SEQUENCE IT BEFORE
  THE LAUNCH - there is no leg-boundary window (B3091):** this rule used to say *defer the commit to a
  leg boundary*, and the third bullet below measured why that cannot work. `scripts/pyramid_gate.py`
  records `engine_inflight` from the engine's own `run_heartbeat.json`, because its `chain_inflight`
  field reads only `serial_chain.log` and a direct run_wave launch never writes there (L865; the
  S6-B3093c false-positive on a dead wave's heartbeat is open).
- **Editing the spec does NOT affect a running wave.** `run_wave.py` reads the spec ONCE at startup
  (`run_wave.py:492`) and the leg loop reads `max_legs` from that in-memory dict (`run_wave.py:245`);
  raising `max_legs` mid-flight changes nothing. A running process holds what it loaded.
- **Killing the engine is not killing the wave.** run_wave is the parent and its leg loop RESPAWNS the
  engine within seconds. **Kill the run_wave root and its descendants, parent-first**, by verified PID.
  `scripts/kill_wave_tree.py` (default dry-run; `--execute` kills) walks UP from the engine to the
  wave-side run_wave / launch_sweep roots and stops at run_serial_chain (B2577, S6-B2573g.c) - **the
  pre-B3096 text said run_wave is not in its target list, stale since B2577** - but it does NOT exclude
  its own pid (its own command line names the out-dir it matches), and it enumerates and kills through
  PowerShell, which is exactly what cannot start under commit exhaustion.

#### Step 2.5 - MONITORING a Step-2 wave

The monitor contract is §8.9. Wave-specific rules:

- **Decide alive-or-dead by the `sim_day_index` DIFF between firings, never by heartbeat age.** The
  heartbeat is written by a SUPERVISOR THREAD, so it stays fresh while workers are frozen (L656) - and a
  STALE heartbeat does not prove death either, since a run at its final sim-day has stopped advancing
  while it writes its cube (L656 addendum). **Both directions are uninformative; only the counter
  carries signal.**
- **The diff interval must exceed the expected per-day time** at the campaign's own measured rate - a
  window showing no movement shorter than one sim-day is normal, not a stall.
- **Read commit availability via GlobalMemoryStatusEx, not PowerShell counters.** Under commit
  exhaustion PowerShell cannot start, so a monitor built on it goes blind exactly when it matters.
  Report FREE COMMIT, never physical RAM (L670).
- **A leg that dies before its cap is resumed SILENTLY by run_wave:** the leg loop continues whenever a
  checkpoint exists and no cube does (`run_wave.py:245-338`). Read the wave's summary log each firing -
  `launch_sweep.py:299-300` writes `CFG=<tag> EXIT=<rc> ELAPSED=<s> CUBE_ROWS=<n|ABSENT>` per leg, and a
  line with ELAPSED under the leg cap and `CUBE_ROWS=ABSENT` is a crash-and-resume (S6-B3094f item 3).
  It resumes from the last PERIODIC checkpoint, which carries no portfolio block, so cash and positions
  restart at that boundary - inert in an isolation cube, where the portfolio holds nothing (S6-B3096g,
  §8.6).
- **Retire the monitor in the same turn the run lands or stops** (CHECKLIST #320) - a monitor that
  outlives its subject keeps re-asserting a frozen state on a timer.

**WHY NOTHING BLOCKED - the loophole, stated plainly (historical, closed at B2520).**
`verify_postconfig_complete.py` then defined `TERMINAL = {"DONE", "SKIPPED", "N/A"}`, so a step marked
SKIPPED **with any reason string** counted as dispositioned and the completeness gate passed.
The gate checks DISPOSITION, not EXECUTION.
A deferral naming a process that does not exist satisfied it indefinitely. The gate STILL checks
disposition - which is exactly why every step now WRITES one, on every run, and why SKIPPED can no
longer be written at all.

**THE RULE, going forward:**

1. **A config is not COMPLETE until all nine steps are DONE or explicitly N/A.** SKIPPED is not a
   disposition; a step that could not run is FAIL or OPEN and BLOCKS.
2. **Step 2 may not launch while any Step-1 config in its lineage carries an outstanding judgment
   step.**
   The decision-bearing unit is the LINEAGE, not the single config: a Step-2 run validates a candidate that Step-1 configs selected.
3. **A ROSTER ADMISSION may not be taken from a config whose judgment steps are outstanding.** Where
   one already has been, the roster row is marked and the admission is re-examined - by the owner's
   word, since an admitted line is closed to re-testing (§1.3, owner 2026-09-12; the pre-B3096 rule,
   which predates that ruling, said only "re-examined").
4. **Any deferral must name an EXECUTABLE target** - a script path that exists and can be run - plus an
   owner and a trigger. Free text describing a future process is a DROP, not a deferral.
5. **Automation is not a substitute for READING the findings.** Battery steps 5-8 run unattended, but
   their output is a list of findings addressed to a human: every judgment-step DONE in the ledger before
   B2520 carried a real finding (a band-level defect, the equivalence-class defect, a grader-loader crash
   found and pinned), and the lens battery's WARN / FAIL rows are the same material, delivered instead
   of deferred. The `LANDING REPORT: <cube>` block is where they are read.
6. **The result reaches the owner mechanically, in the channel the owner reads.** A landing nobody has
   reported is listed in the turn preamble and blocks the Stop hook; "I will summarise it next turn" is

ticketed does not exist (#94). Causes go in only when TESTED - otherwise `UNKNOWN - RCA NEEDED` (#189).

**Battery step 6 - POST-FIX RE-CHECK, if this cycle FIXED anything (CHECKLIST #196).** A fix can
invalidate a conclusion the defect itself left intact: while the bug stood the numbers were

to the owner, never run.

**Battery step 6b - Carrying an equivalence class is FREE for subset-safe parameters only** (§1.5).

**Battery step 7 - IMPLEMENT IN ENGINE: a winner the engine cannot apply is not a winner.**
```bash
python scripts/verify_engine_implemented.py
```
The sweep grades SUBSET-SAFE parameters OFFLINE, which is what makes thousands of combinations
affordable - and also why the search space can contain gates **the engine cannot apply**: the grader

## 6. STEP 3 - ADMIT (both workflows; formerly STEP 4 — ADMIT)

### 6.1 The six live gates

A combination enters Phase 1B only if it clears **all six `LIVE_GATES`** (`roster_core.py:60-61`).
Thresholds re-derived from `backtest/config.py` PASSING_CRITERIA, tier `pooled` (the table was stale on 3
of 6 thresholds until B2402):

| # | gate | bar | config key |
|---|---|---|---|
| 1 | `pooled_sharpe` | **>= 1.0** | min_sharpe_overall |
| 2 | `profit_factor` | **>= 1.3** | min_profit_factor_overall |
| 3 | `sortino` | **>= 1.0** | min_sortino_overall |
| 4 | `psr` | **>= 0.95** | min_psr |
| 5 | `min_trades_holdout` | **>= 15** | min_trades_holdout |
| 6 | `min_trades_full_period` | **> 75** | min_trades_full_period |

- **THE TWO WINDOWS DIFFER.** Gates 1-5 are computed on the **1-year holdout** (HO_START..HO_END =
  2025-05-05 -> 2026-05-05). Gate 6 counts over the **FULL 4-year span** (IS 3.00y + HO 1.00y) - the owner
  kept that counter and restored the 4-year-sized bar (§1.2).
- **TWO GATES ARE THREE-STATE, not two.** `profit_factor` is **NOT EVALUABLE** when a cell has zero losing
  trades: an all-winners cell has pf = inf and `inf >= bar` is True, but a zero-loss sample says nothing
  about the loss side (B2012). `min_trades_full_period` is NOT EVALUABLE when the count is absent,
  because before B1624 a MISSING value PASSED - *unknown* scored better than *known bad*. None is neither
  pass nor fail; it shrinks the denominator so nobody quotes "6 of 6" when 5 were measured.
- **THE POWER FLOOR IS NOT A GATE, AND IS NOT `min_trades_holdout`** (§4.6): a cell below `--min-n` is
  `BELOW_POWER_FLOOR` and never reaches the gates.
- **FOUR CRITERIA ARE DEMOTED to diagnostics and are NOT gates** (`roster_core.DEMOTED`): max_drawdown,
  calmar, deflated_sharpe, win_rate (B1387 / B1436 / B1437). max_drawdown and calmar re-engage at Phase 1B
  on a blended portfolio. The grid stage applies no multiplicity correction across a config's cells
  (owner ruling D2; §1.4).
- **PSR units (B2646, owner ruling 'then c'):** the per-period Sharpe and RAW kurtosis feed the
  Bailey-Lopez de Prado PSR; the annualised Sharpe with excess kurtosis fed before made PSR incomputable
  exactly on strongly-skewed winners.

### 6.3 Which combination advances, and how it enters the roster

1. **Where several qualify: the highest HOLDOUT pooled Sharpe** (owner ruling D3; §4.8) - the gated
   quantity, not the in-sample `is_sharpe`.
2. **`next_pivot_target` is barred as the selected exit** (owner 2026-09-10; §0.3): use the best non-npt
   line that clears all six gates.
3. **ADMISSION DE-DUP (B2666):** every owner-ruled admission set passes the funnel's Jaccard-0.70 de-dup

6. **Count the REGISTERED mirror short** (S6-B2417); a missing mirror is created under the standing

7. **The remaining ADMISSION step, where the admitted parameters are real engine knobs, is a

8. **Report the verdict WITH its denominator** (#182): *"N of M combinations passed, across X of Y

## 7. THE LOCKED REPORTING STANDARD - CHECKLIST #183 (owner-locked B1510; formerly §6)

Every strategy's optimisation is reported through `scripts/producer_variant_table.py` as ONE artifact.

### 7.1 Section 1 - the BOOLEAN FORMULA (REQUIRED; a SPEC without it is rejected)

The header must state the formula is READ from source, never recalled. Two layers, shown here with
placeholders - every real formula lives in its strategy's SPECS entry and Table A file:

```
=============================== PRODUCER LAYER ===============================

P1  events  =  <producer_function>( ohlc, <param_a> = <production value> )
                   -> what it emits, in plain language
                   PARAMETER: <param_a> = <production value>   (library default, if any)

P2  derived =  <second step>( P1, <param_b> = <production value> )
                   PARAMETER: <param_b> = <production value>

P3  per event e:   e.<property> = ( <condition on P2> )
                   -> no parameter; derived from P2

=============================== STRATEGY LAYER ===============================

<gate_signal>    =  AT LEAST ONE event e in P1 satisfies ALL of:
                        ( <clause> )                        [from P2]
                        AND ( e.<property> )                [from P3]

fires            =  ( <gate_signal> )  AND  ( <second leg> ) [from P<n>]
```

**Rules the format enforces.** Every producer gets a `Pn` id, its call signature with the LIVE
production value inline, a plain-language note on what it emits, and an explicit `PARAMETER:` line - or
`no parameter` where none exists. The STRATEGY LAYER spells out `AT LEAST ONE ... ALL OF` rather than
symbolic OR/AND, and tags every clause with the `Pn` it came from, so a reader can walk from any gate
back to the producer that computes it. A breadth campaign adds a BREADTH LAYER listing its B-axes (§3.6).
**Why Section 1 exists at all:** a strategy was once called untunable because its gate read as two
booleans; forcing the producer layer to be written first makes that error unwritable - those booleans
had six parameters behind them (L355). The first worked formula is in the campaign log (B.16).

the **free-vs-resim split**. Hand-counting reintroduced the exact error #182 exists to prevent (L368: a
hand-counted "3 of 6" was really "3 of 5").

### 7.8 Drift guard

`validate_spec()` **blocks generation** when a `Pn` appears in Section 1 but has no Table A row, or vice
versa, and rejects any SPEC lacking a formula. Section 1 and Table A are two views of one inventory, and
a hand-maintained pair diverges. Verified against three drift modes and in BOTH directions, per the
B1504 lesson that a gate exercised one way may block everything (L375).

### 8.2 What demand pruning skips, and when (formerly REFERENCE — WHAT GETS SKIPPED, AND WHEN)

Demand pruning computes only the producers whose signal keys the ACTIVE strategies actually read.
**It arms in three stages:** bars 1-25 compute EVERYTHING and RECORD reads; the skip set is derived and
pruning arms; from then on the signals dict is wrapped in `GuardedSignals`, so reading a pruned-away key
RAISES `SkippedSignalError` instead of returning `.get()`'s default.

**The required-key set is built by BOTH methods, unioned (B1570):**
- **RUNTIME recording** catches keys built at runtime - a static scan sees only one of a strategy's two
  keys when the second is built from a knob (L437).
- **STATIC extraction** catches keys a boolean SHORT-CIRCUITED past: in `s.get(a) and (s.get(b) or ...)`,
  if `a` is False across every warmup bar the `and` never evaluates its right side, so `b` is never READ
  and its producer would be pruned (L444).

The two fail in COMPLEMENTARY directions; the union is strictly safer - it can only KEEP more producers.
Each strategy keeps exactly the primitives its keys need, so a producer shared by several strategies is
kept for any of them automatically. The first measured effect (on one strategy) is in the campaign log.

**Phase 1B is different - pruning is INERT there by design.** `STRATEGY_SUBSET_FILE` is an
OPTIMISATION-ONLY device; Phase 1B simulates all passed strategies together, where every producer is read
anyway. With no subset file, `wrap()` returns **the same object** (identity-pinned by test) and
`smc_skip_primitives()` returns empty - **zero overhead, zero behaviour change**. Never set the subset
file for a Phase 1B or full-roster cube run.

### 8.3 Measured costs, and why a percentage alone is a lie (formerly §10.2 and REFERENCE — MEASURED COSTS)

```
0.2613 s per ticker-day   (pool=10; two concordant points, 10pct apart:
                           0.2484 @ 50t x 4y, 0.2743 @ 20t x 2y)
per run  =  tickers x sim-days x 0.2613      <- a CANONICAL rate; a campaign's own rate supersedes it
100 tickers x 1003 days (4y)  ~= 7.3 h
544 tickers x 1003 days (4y)  ~= 39.7 h      <- 7.3 h x (544/100), rescaled B1618
200 tickers x 1y (the ruled Step-1 shape): 2.0 / 2.1 / 4.0 h per config, measured at pool 0
                           on one family's Step-1 chain, 2026-09-02 (serial_chain.log)
```

| shape | measured |
|---|---|
| 182 strategies, 100 tickers, 2y, pool=10 | **4.56 h** (2.63 h day loop + 1.93 h post-processing) |
| 182 strategies, 20 tickers, 2y, pool=3 x3 concurrent | 3,696 s |
| **1 strategy, 5 tickers, 2y, pool=0, UNPRUNED, cold cache** | **1,920 s** (B1568) |
| **1 strategy, 5 tickers, 2y, pool=0, UNPRUNED, warm cache** | **703 s** (B1569b) |
| **1 strategy, 5 tickers, 2y, pool=0, PRUNED, warm cache** | **366 s** (B1569b) |
| the ruled Step-1 shape (200 tickers x 1 year), one family's chain at pool 0 | 2.0 / 2.1 / 4.0 h per config (B2573, `serial_chain.log`) |
| Machine | 10 physical / 12 logical cores, 15.6 GB RAM |

- **A campaign's own measured rate beats the canonical one.** The canonical 0.2613 s per ticker-day is a
  pool=10 figure, and real runs sit on both sides of it: sequential runs at 200 tickers measured 85.5-127.9
  s per sim-day against its 52.3 s, while pooled Step-2 waves at 544 tickers ran faster than its 142 s
  (80 s per sim-day at pool 10, 49.49 s at pool 6 - campaign log). The per-day cost also varies with the
  parameter swept, so run_wave re-projects from each leg's own rate (B2127). For a ONE-strategy config,
  post-processing is NOT on the slow path: 2.2 of 198 minutes (1.1 pct) on one measured pair (B1915) -
  unlike the 182-strategy run in the table above, where it was 1.93 of 4.56 h.
- **THE SAME UNPRUNED CONFIG TOOK 1,920 s AND 703 s - 2.7x apart, same machine, same code,** differing
  only in OS file-cache warmth. So: (1) **cross-session elapsed times are NOT comparable** - A/B arms run
  BACK-TO-BACK in one session; (2) **a saving is a fraction OF A BASELINE, and the baseline's composition
  is not constant** - pruning measured 14.64 pct against a cold baseline and 47.94 pct against a warm
  one, so quote a saving WITH its cache condition, never alone; (3) comparing the pruned warm arm
  (366 s) to the cold baseline (1,920 s) would report 81 pct, two-thirds of it filesystem cache - the
  trap re-running the baseline exists to avoid.
- **Correctness bar for any optimisation claim:** the cube must be BIT-IDENTICAL, not merely
  same-row-count (the B1568 + B1569b cubes all hash to `615233dbab2756d0`, 1,352 x 37).
- **Never extrapolate from one point.** Five extrapolations were wrong in one session: 9x light (L367),
  23 pct light (L377), ~100x heavy (L383), flat scaling read from noise (L401), and a profiler share
  mistaken for a wall-clock saving (L418). **Two concordant measurements minimum before any
  projection.**

### 8.4 Parallelism and throughput (formerly REFERENCE — PARALLELISM and the B2142 throughput measurements)

- **Always set `--screen-pool-workers` explicitly** - the default 0 is SEQUENTIAL (L407). On a 12-core
  box `pool=10` measured **1.53x** like-for-like; it is not more because ~62 pct of per-day work is
  serial.
- **Every run in programme history until 2026-08-24 was single-threaded:** `run_wave.py` hardcoded
  `--screen-pool-workers 0` (1 of 10 cores, confirmed live at 97 pct of one core via Get-Process);
  `pool_workers` has been spec-driven since B2142 (default 0,
  so no legacy spec changes behaviour). The N=3 concurrency figure (2.04x per arm, S6-B1552a) was
  measured in that pool-OFF regime - **the pool dividend and the N-way concurrency dividend draw on the
  SAME cores and must never be multiplied** (council-verified, B2142).
- Pool ON at 50 tickers: 3.21x screening, 2.33x end-to-end (the b2128 probe pair). Pool ON at 200
  tickers: **60.7 s/sim-day** against 85.5-127.9 sequential - the pool buys ~1.4-2.1x at full width and
  **the speedup decays with universe size**; DERIVED config cost 60.7 x 250 days ≈ **4.2 h**, which is
  what moved the owner's local cap from 3 h to 5 h (it fits the 5 h cap un-chunked, ~19 pct
  headroom). One pooled arm measured ≈ 5.3 GB of 15.6 GB
  (main 311 MB + 10 workers at 468-584 MB), so N=2 pooled would fit RAM but split the same cores.
- **Run configs CONCURRENTLY rather than widening the pool** - in-run parallelism caps at ~1.6x
  (Amdahl, ~62 pct serial), and separate processes scale far better (B1558 measured 2.24x throughput at
  3-way). **Never let total workers exceed physical cores** - pool=60 on one ticker ran 11.6x SLOWER
  than sequential (L-pool).
- **COMMIT, not physical RAM, is the binding memory quantity** (B2229 / L670; §4.5 Step 1.0 b).
- **Do NOT run a pyramid or any other CPU work during a timing A/B** - it inflates the arm in flight and
  biases the saving upward (L621). **Do not run the full suite beside a live wave either** - there the
  risk is commit exhaustion, not timing (§4.9 Step 2.4).

### 8.6 RUN-SAFETY ARCHITECTURE - the launch stack as it actually is (B2142-B2169, 2026-08-24/25)

Built after one arm ran 2.9 h against a 2.5 h cap with no kill, no warning and no checkpoint, computing
blind for 2 h 34 min. Every mechanism below exists because a specific failure was measured, and every
one carries a pin.

- **The cap is TWO-LAYER** (owner ruling 2026-08-24: 5 hours, recorded as the executable constant
  `OWNER_LOCAL_CAP_HOURS = 5.0` in `scripts/prelaunch_gate.py`, which **fails CLOSED**: a manifest
  declaring NO leg cap is refused - L642, the check was briefly `if cap is not None`, which converted
  "undeclared" into "approved"). Inside the engine: the in-loop per-day check (B2132), plus the **B2148
  supervisor** - a daemon thread armed before the first iteration that samples wall-clock on its own
  schedule and hard-exits at the cap wherever the loop is. L637: the engine had SEVEN loop-gated guards
  and writers (telemetry, progress, the 50-day site, the kill, three checkpoint writers) and one long
  sim-day silenced all seven at once - a guard must not share the control flow it guards; B2145 freezes
  the loop-gated writer count so an eighth cannot join silently. The cap counts ACTIVE hours (§1.3).
- **Observability is session-agnostic by construction.** The supervisor writes **`run_heartbeat.json`**
  every ~30 s (atomic tmp+replace): elapsed_hours, sim_day_index, sim_date, closed/open trades, cap,
  pid, timestamp. Progress lives in the filesystem - any session, or none, can read it; session-held
  monitors and crons are convenience only (they died with a session restart on 2026-08-24 and the run
  computed blind; L637 / S6-B2143b). A killed run's launcher log is shape-identical to a live one (L641):
  the CFG completion line is written only on normal exit, so **`scripts/classify_run_log.py`** is the
  authoritative reader - COMPLETE / DEAD_WITHOUT_ENDING / RUNNING, one-directional: no ending + no live
  pid = DEAD, never RUNNING (pin `test_b2158`).
- **On a wall-time kill the SUPERVISOR flushes `engine_state.json` (with the portfolio block), the
  trade-log checkpoint and the open-book checkpoint** through an out-of-loop emitter, so a killed run
  stays resumable (B2126 proved kill-then-resume live; B2148 proved it for a hung sim-day). **The other
  writers save less (MEASURED B3096, S6-B3096g):** the in-loop kill flushes the open book only once a
  trade has closed, so a kill before the first close can leave a run the resume refuses, and neither it
  nor the periodic checkpoint writes the portfolio block, so a resume from either restarts cash and
  positions (logged as a pre-B2387 checkpoint) - inert in an isolation cube, which never mirrors a
  trade into the portfolio (`backtest.py:3379-3380`), and real for a non-isolated run. **A resume RESTORES the open book** - it reads
  `open_trades_checkpoint.csv` and HALTS on a count mismatch rather than continue partial

  B3096 are FIXED AT B3098: the regime map is rebuilt at every resume (S6-B3094c, §4.8), and a resume

  kill past the 5 h owner cap) can leave a half-run day, which is skipped and recorded in

  9-leg split run matched the unsplit run's cube (`output_audit/b3098_resume_equivalence.json`). STILL
  OPEN, measured by the same run: the sizing and skipped-trade logs are not carried across a resume

  open book, of the portfolio block or of these defects.)
- **B2167 caveat on historical data:** every `engine_state.json` written before B2167 records

  `test_b2167` bans phantom getattr-self names engine-wide.
- **The pre-run gate** (CHECKLIST #158/#160/#161 - wired, hardened B2149-B2169):

### 8.10 Design principle for NEW producers (B2182, external item 10 adopted)

Prefer parameter-free formulations at design time: ensembles across lengths (mean of signs -> one

over fixed ones. Every parameter deleted is a selection-bias dimension that never needs correcting - and
EVENT triggers carry fewer tunables than STATE definitions. Applies FORWARD (new producers / Class 7
wires); retrofits are per-strategy owner-approval work.
